Milestones and gating rules are defined in `docs/SPANOVA_MASTER_SPEC.md`
section 20, with content remapped per
`docs/ARCHITECTURE_AMENDMENT_V2.md` (P06/P07 now target MIDAS NX, not
ALLPLAN; P12 now covers SCIA and, if wanted, ALLPLAN). This file tracks
status only. Never start a milestone marked "Not started" without the

C#/.NET/Avalonia stack (see `archive/v2-csharp-avalonia/`), then the
engineer moved the whole platform to the stack below. Status resets to

completed prerequisite.

## Site/Corridor & Bridge Layout Platform - new track

A separate, additive track opened 2026-09-10 (engineer-initiated
architecture change - see `docs/SITE_LAYOUT_PLATFORM_ANALYSIS.md`
sections A-Q for the full proposal). Numbered independently of P00-P12,
same pattern as the P06 MIDAS-P01/P02 sub-milestones. Two changes to the
existing plan came out of this: (1) SPANOVA gets its own native
linear-elastic analysis engine and stops using MIDAS NX during
generation/optimization - MIDAS NX is kept only as a post-selection,
high-fidelity verification tier (addendum P); (2) bridge length,
abutment/pier positions become design variables generated by a new
`BridgeLayoutEngine`, not typed in by hand.

| Milestone | Scope | Status |
|---|---|---|
| SITE-P01 | `spatial-core` + `alignment` modules: `CoordinateSystem`, `Point3D`, chainage<->XYZ conversion for straight alignments, unit-tested against hand-verified reference points | **Done** (this session) - see `docs/architecture.md`'s SITE-P01 section |
| LAYOUT-P01 (revised, addendum Q) | `constraints` + `bridge-layout` modules + `POST /api/layout/generate` + "Site & Layout" frontend screen: one straight `Alignment` + one `BridgeSite` + `NoPierZone`(s) -> candidate C1/C2 abutment chainages + candidate piers + feasible/rejected `BridgeLayoutAlternative`s, traceable via `ConstraintCheckResult`, shown in a table with per-alternative rejection reasons. No terrain, no pier/abutment height, no FEM, no map, no 3D. | **Done end-to-end** (this session) - see `docs/architecture.md`'s LAYOUT-P01 sections |
| Native analysis engine (addendum P) | `spanova-analysis-engine`: linear-elastic direct stiffness method, 3D frame elements, elastic-link bearings, `POST /api/fast-solver/solve`, SPANOVA Fast Solver frontend screen | **Done** (this session) - validated against closed-form results and the engineer's own 5-span frame-bridge test case; see `docs/architecture.md`'s matching section |

Constraint/terrain/geotechnical/hydraulic modules, the 2D map (MapLibre),
3D visualization (Three.js), and Site Intelligence providers all remain
**further out** on the roadmap per `docs/SITE_LAYOUT_PLATFORM_ANALYSIS.md`
section L - not scoped into any milestone yet.

## P07 loads/bearing/soil - engineering scope agreed, modelling deferred

Engineer supplied real answers for the MIDAS analysis extensions
(replacing VIA-35's current simplifications - see the "P06 - real
project validation" section above) before pausing to work on P10
instead. Recorded here so this isn't re-litigated when work resumes:

- **Soil/foundation**: still out of scope - pier bases stay fixed
  (ankastre). Not being modelled yet, by choice.
- **Code basis**: base EN values throughout, no National Annex
  adjustment (alphaQi = alphaqi = 1.0).
- **Bearings**: always elastomeric, modelled as MIDAS `ELNK` (elastic
  link - schema verified: `NODE:[i,j]`, `SDR:[Kx,Ky,Kz,Krx,Kry,Krz]`).
  Kx/Ky/Kz are external inputs (the engineer supplies numeric values per
  project) - **requires restructuring the model**: bearing points need
  two separate nodes (pier-top + girder-end) connected by the link,
  instead of today's single shared node.
- **Loads**: full 12-category taxonomy from the engineer's own list
  (Self Weight/Superimposed Dead, Traffic, Pedestrian, Temperature, Wind,
  Seismic, Braking/Acceleration, Centrifugal, Settlement, Construction,
  Special, Load Combinations) should exist in the domain model/menu
  structure, but only **traffic load = EN 1991-2 LM1** gets computed for
  now - the rest come later, one at a time.
- **Traffic load (LM1)**: MIDAS's own Eurocode vehicle library
  (`/db/MVHL`, `VEH_EUROCODE.SEL_VEHICLE`) already encodes LM1's real
  characteristic tandem/UDL values - SPANOVA does not compute or invent
  these, just selects LM1 and sets the adjustment-factor arrays to 1.0
  (base EN, per the engineer). Carriageway width = deck width - left
  walkway - right walkway (walkways confirmed 1.00 m each on VIA-35;
  `Bridge`/`Deck` will need explicit `leftWalkwayWidthM`/
  `rightWalkwayWidthM` fields, not currently modelled). Notional lane
  count/width follows EN 1991-2 Table 4.1 exactly - **verified the real
  rule is 3.00 m per lane**, correcting the engineer's own first guess of
  3.50 m (flagged and confirmed before use, not silently substituted).
- **Extra dead loads**: external input (the engineer supplies specific
  values, e.g. wearing surface/barriers) - `/db/CNLD` (nodal point loads)
  and `/db/BMLD` (element distributed loads) schemas both verified as
  candidates.
- **Girder model**: expand from today's 1 representative girder line to
  a real 6-parallel-girder model, connected transversely by **simple
  rigid links** at each cross-section (not a full slab/plate grillage) -
  the engineer's own explicitly-chosen simplification, needed because
  MIDAS's traffic-lane system (`/db/LLAN`) distributes load by
  eccentricity relative to real girder positions, which a single-beam
  model can't represent correctly.
- **Not yet verified live**: the full LM1 wiring
  (`LLAN` + `MVHL` + `MVLDeu` moving-load case + `MVCT` analysis control)
  turned out to be a much deeper, more nested schema than MIDAS-P01's
  simple `NODE`/`ELEM`/`MATL`/`SECT` calls - agreed with the engineer to
  build and verify this in two checkpoints when work resumes: (A) 6
  girders + bearings + fixed piers, self-weight only, verified live
  first; (B) LM1 traffic load added on top of the verified (A) model.
